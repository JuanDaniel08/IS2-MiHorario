# Usar Node.js con NestJS para el Backend y API

* Estado: Propuesto
* Decidentes: Angie - Daniel
* Fecha: 2026-09-09
* Historia técnica: ESC-REN-0001 / ESC-REN-0007 / Escenario 6.4 (Coherencia Matemática de Horas) / Escenario 6.7 (Tiempo de Respuesta Programación Automática)

## Contexto y planteamiento del problema

La plataforma MiHorario requiere procesar mallas de turnos complejas para grupos de más de 50 a 100 empleados en tiempo real, ejecutar validaciones matemáticas de jornadas laborales (horas ordinarias, recargos y descansos conforme a la ley colombiana) en menos de 2 segundos, y ofrecer APIs reactivas para dispositivos móviles y web con tiempos de respuesta inferiores a 2 segundos bajo cargas concurrentes de más de 100 usuarios activos.

Adicionalmente, el equipo de desarrollo necesita una plataforma que maximice la velocidad de entrega (*time-to-market*), facilite el tipado estricto y ofrezca una estructura de código escalable que evite la degradación del sistema a largo plazo.

¿Qué lenguaje y framework de backend deberíamos seleccionar para maximizar la velocidad de desarrollo, garantizar un alto rendimiento en operaciones concurrentes de I/O y mantener una arquitectura modular fuertemente tipada?

## Impulsores de decisión

* **Escenario de calidad (Rendimiento y Carga Inicial - ESC-REN-0001 y ESC-REN-0007):** El backend debe responder a consultas y peticiones de asignación en menos de 2 segundos manteniendo consistencia operativa bajo al menos 100 usuarios simultáneos en horarios pico.
* **Escenario de calidad (Rendimiento en Algoritmos y Validación - Escenario 6.4 y 6.7):** La API debe ejecutar la validación de coherencia matemática de horas en menos de 2 segundos y coordinar la propuesta de programación automática en segundo plano sin bloquear el hilo de ejecución principal.
* **Restricción técnica (Mantenibilidad y Tipado Estricto):** Se requiere un lenguaje fuertemente tipado que reduzca errores en tiempo de compilación y facilite la unificación de contratos de datos (DTOs) y validación declarativa (*Fail-Fast*).
* **Restricción técnica (Arquitectura Modular):** El framework debe obligar o promover por diseño la separación de responsabilidades en módulos independientes y cohesivos, alineado con la directriz de arquitectura modular del proyecto.
* **Restricción de negocio (Time-to-Market y Productividad):** Reducir la fricción cognitiva y la duplicidad de modelos compartiendo conocimientos y tipados con la capa frontend (TypeScript).

## Opciones consideradas

* Opción 1: Node.js con NestJS (TypeScript)
* Opción 2: Java con Spring Boot
* Opción 3: Python con FastAPI
* Opción 4: C# con .NET Core (ASP.NET Core Web API)

## Resultado de la decisión

Opción elegida: "Node.js con NestJS (TypeScript)", porque combina un modelo de I/O asíncrono no bloqueante de alto rendimiento basado en el *Event Loop* de Node.js con una arquitectura empresarial modular fuertemente inspirada en Angular y Spring (inyección de dependencias, controladores, módulos, proveedores y decoradores). TypeScript proporciona tipado estricto y validación declarativa de datos con `class-validator` desde el punto de entrada de las peticiones (*Fail-Fast*), acelerando la velocidad de desarrollo al unificar el ecosistema de lenguaje con el frontend, y manteniendo un consumo de memoria ligero idóneo para despliegues en contenedores serverless o PaaS.

### Consecuencias positivas

* **Modelo I/O no bloqueante:** Atiende concurrentemente más de 100 usuarios activos consultando agendas e interactuando con la base de datos sin saturar los subprocesos del servidor (ESC-REN-0007).
* **Arquitectura modular y organizada por defecto:** NestJS estructura el código de forma natural en módulos (`SchedulingModule`, `EmployeeModule`, `PayrollModule`, `AuditModule`), evitando el código espagueti y sentando las bases para una Arquitectura Limpia.
* **Tipado estricto y validación automática:** TypeScript junto a *Pipes* y DTOs permite validar esquemas de entrada antes de tocar la lógica de negocio, descartando peticiones erróneas en milisegundos (táctica *Fail-Fast* del Escenario 6.1).
* **Unificación de stack tecnológico:** Al usar TypeScript tanto en cliente como en servidor, se comparten interfaces, modelos de validación y utilidades de fechas, reduciendo la curva de aprendizaje y el tiempo de implementación.
* **Ecosistema rico para tareas asíncronas y WebSockets:** Soporte nativo para colas en segundo plano (BullMQ/Redis) y WebSockets para actualización de horarios en tiempo real (ESC-TRA-0003).

### Consecuencias negativas

* **Rendimiento limitado en procesamiento CPU-Intensivo mono-hilo:** Si el algoritmo de generación automática de turnos (Escenario 6.7) requiere cálculos combinatorios masivos que bloqueen el *Event Loop*, debe delegarse a *Worker Threads* o a un servicio especializado en segundo plano.
* **Disciplina arquitectónica requerida:** Aunque NestJS promueve patrones de diseño sólidos, la flexibilidad de JavaScript/TypeScript requiere convenciones de equipo estrictas para evitar fugas de responsabilidades entre capas.

## Pros y contras de las opciones

### Node.js con NestJS

Framework progresivo de Node.js construido con TypeScript que implementa patrones empresariales robustos (IoC, DI, CQRS).

* Bien, porque su arquitectura modular e inyección de dependencias facilitan el mantenimiento y testing unitario de las reglas de negocio.
* Bien, porque el modelo asíncrono es altamente eficiente en operaciones I/O (lecturas a CockroachDB, llamadas a APIs externas como Teams y Firebase).
* Bien, porque comparte lenguaje (TypeScript) y contratos de datos con el frontend, acortando el *time-to-market*.
* Bien, porque tiene un arranque rápido (*fast boot*) y bajo consumo de memoria base (<150 MB por instancia), ideal para escalado horizontal elástico.
* Malo, porque no es óptimo para algoritmos puramente intensivos en CPU sin delegación asíncrona a workers o procesos satélite.

### Java con Spring Boot

Framework empresarial líder en la industria para el desarrollo de APIs robustas en Java.

* Bien, porque cuenta con una madurez excepcional, tipado estricto de primer nivel y un ecosistema gigantesco de librerías para auditoría y seguridad (Spring Security).
* Bien, porque su soporte multihilo nativo es excelente para cálculos numéricos concurrentes pesados.
* Malo, porque el consumo de memoria RAM base es elevado (frecuentemente >400-600 MB por contenedor), incrementando los costos operativos en infraestructura cloud.
* Malo, porque la verbosidad de Java y los tiempos de compilación ralentizan el ciclo de prototipado y entrega frente a TypeScript.
* Malo, porque fragmenta el stack tecnológico del equipo entre dos ecosistemas disjuntos (Java en backend vs. TypeScript/JavaScript en frontend).

### Python con FastAPI

Framework moderno, rápido (de alto rendimiento) para la construcción de APIs con Python 3.8+ basado en anotaciones de tipo estándar.

* Bien, porque es sumamente rápido para escribir código y posee una integración nativa con librerías matemáticas y de optimización (como OR-Tools, SciPy, PuLP) ideales para el algoritmo de asignación de turnos (Escenario 6.3).
* Bien, porque la validación con Pydantic y documentación OpenAPI es automática y de alto nivel.
* Malo, porque no provee un sistema estructurado de inyección de dependencias ni un estándar arquitectónico modular empresarial tan maduro como NestJS o Spring Boot para aplicaciones empresariales medianas/grandes.
* Malo, porque la gestión de concurrencia y transacciones multi-recurso en Python requiere cuidados adicionales para evitar contención en el GIL (*Global Interpreter Lock*).

### C# con .NET Core (ASP.NET Core)

Plataforma de alto rendimiento multiplataforma de Microsoft para aplicaciones backend empresariales.

* Bien, porque ofrece uno de los mejores rendimientos en benchmarks de peticiones HTTP concurrentes de la industria.
* Bien, porque su tipado estricto y biblioteca de clases base son muy consistentes y profesionales.
* Malo, porque impone una curva de adopción y herramientas específicas si el equipo tiene mayor afinidad con el ecosistema web moderno.
* Malo, porque no ofrece la interoperabilidad y reutilización de tipos directa con el cliente web/móvil que brinda TypeScript.
