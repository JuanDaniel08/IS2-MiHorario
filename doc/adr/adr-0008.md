# Estrategia de Caché en Memoria con Redis para Optimización de Consultas de Turnos y Catálogo de Parámetros

* Estado: Aceptado (Validado empíricamente mediante PoC-0008)
* Decidentes: Angie - Daniel
* Fecha: 2026-09-16
* Historia técnica: ESC-REN-0007 (Concurrencia de 100 Usuarios Activos) / ESC-REN-0001 (Tiempo de Respuesta <2s) / Escenario 6.7 (Programación Automática <3s) / Escenario 6.4 (Reglas Laborales y Coherencia Matemática) / ADR-0001 / ADR-0004

## Contexto y planteamiento del problema

En la operación de MiHorario, el patrón de acceso a los datos presenta una marcada asimetría de lectura frente a escritura (*read-heavy*):
1. **Picos masivos de consulta concurrente:** En los momentos de publicación de una nueva malla semanal o durante el cambio de jornada operativa, decenas o cientos de empleados y supervisores consultan simultáneamente el mismo calendario de turnos. Conforme al requerimiento **ESC-REN-0007**, el sistema debe responder en menos de 2 segundos bajo una carga concurrente de al menos 100 usuarios activos.
2. **Cómputo iterativo en algoritmos de asignación:** El motor de programación automática de turnos (**Escenario 6.7**) y la validación matemática de jornadas laborales (**Escenario 6.4**) evalúan cientos de combinaciones de empleados contra restricciones de descanso, límites de horas legales y matrices de tiempos de traslado entre zonas distantes del parque Comfama.
3. **Catálogo de parámetros y plantillas de mensajes:** Las reglas operativas, matrices de distancias y plantillas de comunicación son datos de alta lectura que cambian con muy baja frecuencia.

Si cada una de estas consultas concurrentes y cálculos algorítmicos impacta directamente el motor de base de datos relacional distribuida (CockroachDB, [ADR-0001](adr-0001.md)), se generará una sobrecarga innecesaria en el pool de conexiones y latencias acumulativas de E/S en disco, degradando los tiempos de respuesta y encareciendo los costos de computación por unidades de petición (Request Units).

¿Cómo debe estructurarse una capa de almacenamiento en memoria intermedia para optimizar las consultas repetitivas de turnos, servir parámetros de reglas al instante y blindar la base de datos principal ante picos de alta concurrencia?

## Impulsores de decisión

* **Escenario de calidad (Rendimiento y Concurrencia - ESC-REN-0007):** El sistema debe responder en menos de 2 segundos manteniendo consistencia operativa bajo al menos 100 usuarios activos consultando la agenda simultáneamente.
* **Escenario de calidad (Rendimiento Algorítmico - Escenario 6.7):** La propuesta de horario automático debe calcularse y presentarse en menos de 3 segundos, lo cual exige que las matrices de reglas y perfiles de operarios se lean desde memoria RAM a velocidad de submilisegundos.
* **Escenario de calidad (Disponibilidad y Protección de la Persistencia - ESC-DIS-0001):** Proteger el clúster transaccional de CockroachDB de saturación por consultas de lectura redundantes, preservando sus recursos para transacciones de escritura y publicación estricta ("Doble Candado" del Escenario 6.1).
* **Restricción técnica (Simplicidad y Reutilización de Componentes):** Aprovechar la instancia de Redis ya seleccionada en el [ADR-0004](adr-0004.md) para la cola de mensajería (BullMQ), reduciendo la multiplicidad de motores de infraestructura.
* **Restricción de negocio (Consistencia de Datos y No Ambigüedad):** Garantizar que la caché nunca sirva turnos obsoletos o revocados a los operarios tras una reasignación aprobada por un supervisor.

## Opciones consideradas

* Opción 1: Caché en memoria distribuida con Redis utilizando el patrón Cache-Aside con invalidación orientada a eventos
* Opción 2: Caché en memoria local del proceso de la aplicación (In-Memory Cache con Node.js / Node-Cache / LRU)
* Opción 3: Lectura directa exclusiva en la base de datos relacional con réplicas de lectura (CockroachDB Follower Reads)
* Opción 4: Caché en base de datos documental auxiliar (MongoDB / DynamoDB como acelerador)

## Resultado de la decisión

Opción elegida: "Caché en memoria distribuida con Redis utilizando el patrón Cache-Aside con invalidación orientada a eventos", porque centraliza el almacenamiento de datos temporales y catálogos en una estructura de clave-valor ultrarrápida en RAM compartida entre todas las instancias de backend, con las siguientes directrices técnicas:

1. **Patrón Cache-Aside (Lazy Loading):** Cuando el backend NestJS recibe una petición de consulta de agenda (`GET /schedules?week=X&dept=Y`), primero consulta la clave en Redis (`schedule:week_X:dept_Y`). Si existe un acierto de caché (*Cache Hit*), la respuesta se serializa y retorna en menos de 10 milisegundos. Si no existe (*Cache Miss*), se consulta CockroachDB, se almacena el resultado en Redis con un Tiempo de Vida (*Time-To-Live - TTL*) de 15 minutos, y se entrega al cliente.
2. **Invalidación proactiva orientada a eventos:** Cada vez que un supervisor aprueba, modifica o elimina un turno (evento transaccional registrado en CockroachDB), el servicio emite un evento interno que elimina inmediatamente las claves de caché afectadas (`DEL schedule:week_X:*`). Esto asegura consistencia estricta y previene que los empleados vean datos desactualizados.
3. **Catálogo de Parámetros y Mensajes en Redis Hashes:** Las reglas de jornada laboral máxima (reducción gradual de jornada en Colombia), las matrices de distancias entre zonas (Escenario 6.3) y las plantillas de notificación del catálogo de mensajes se cargan en Redis usando estructuras *Hashes*. El motor de asignación automática (Escenario 6.7) realiza lecturas en microsegundos de estos parámetros sin tocar disco, resolviendo la matriz de combinaciones en <3 segundos.
4. **Sinergia con la infraestructura existente:** Al emplear el mismo clúster de Redis gestionado (Google Cloud Memorystore / Redis Cloud) que orquesta las colas de BullMQ ([ADR-0004](adr-0004.md)), se optimizan los costos de operación y se simplifica la topología de red dentro de la VPC.

### Consecuencias positivas

* **Respuesta en submilisegundos ante picos de lectura:** Más del 85% de las consultas de calendarios se resuelven desde la memoria RAM de Redis en tiempos de entre 2 y 15 ms, garantizando el cumplimiento de ESC-REN-0007 y ESC-REN-0001.
* **Aceleración crítica del cálculo de turnos (Escenario 6.7):** El algoritmo de programación automática dispone de las reglas y tiempos de traslado en memoria inmediata, reduciendo el tiempo de procesamiento de la matriz a menos de 3 segundos para plantillas de más de 50 colaboradores.
* **Descarga operativa sobre CockroachDB:** Reduce drásticamente las operaciones de lectura en la base de datos distribuida, liberando conexiones y presupuesto de Request Units para operaciones críticas de escritura.
* **Estado compartido entre múltiples réplicas:** A diferencia de una caché en memoria de proceso, Redis es externo al contenedor de Cloud Run ([ADR-0006](adr-0006.md)); si Cloud Run escala dinámicamente de 1 a N instancias, todas comparten la misma visión homogénea de la caché.

### Consecuencias negativas

* **Riesgo de inconsistencia temporal ante fallas de invalidación:** Si la lógica de invalidación no cubre todas las variantes de claves tras una edición de turno, un usuario podría consultar un horario no actualizado hasta que expire el TTL (15 minutos). Se mitiga con pruebas unitarias sobre los interceptores de caché y TTLs cortos y conservadores.
* **Consumo de memoria RAM y costo de clúster:** Redis almacena todo en memoria RAM. Es imperativo establecer políticas de desalojo claras (`maxmemory-policy: allkeys-lru`) y comprimir los payloads JSON grandes para evitar desbordamientos de memoria.

### Validación Empírica mediante PoC (Hypothesis-Driven Design)

Conforme a la metodología **HDD (Hypothesis-Driven Design)** de la asignatura, la decisión fue validada empíricamente en el experimento **[PoC-0008: Caché con Redis](../../poc/poc_0008-redis-cache/README.md)** mediante benchmarking de 100 usuarios activos concurrentes:

* **Cumplimiento ESC-REN-0007:** La ráfaga de 100 consultas se resolvió en 151 ms en memoria RAM (frente a 750 ms en base de datos directa), cumpliendo holgadamente con el SLA de < 2.000 ms.
* **Protección de CockroachDB (ESC-DIS-0001):** Reducción del **99.0%** en lecturas directas a la base de datos distribuida (solo 1 consulta *Cache Miss* en frío gracias a la deduplicación *Single-Flight*).
* **Consistencia e Invalidación Proactiva:** Se verificó que tras la aprobación de una modificación de turno, la clave en Redis se elimina de inmediato (`DEL schedule:week_X`), garantizando cero lecturas de turnos obsoletos.

## Pros y contras de las opciones

### Redis Distribuido con Cache-Aside

* Bien, porque ofrece tiempos de lectura de submilisegundos (en RAM), soportando fácilmente más de 100 usuarios activos simultáneos (ESC-REN-0007).
* Bien, porque permite compartir el estado de caché entre múltiples réplicas elásticas de Cloud Run (ADR-0006).
* Bien, porque provee estructuras nativas (Hashes, Sets) ideales para el Catálogo de Parámetros y Catálogo de Mensajes.
* Bien, porque reutiliza la infraestructura de Redis ya adoptada para el Message Broker con BullMQ (ADR-0004).
* Malo, porque añade un punto de dependencia adicional en la red y exige disciplina rigurosa en las políticas de invalidación y TTL.

### Caché Local en Memoria de Proceso (Node.js Heap / LRU Cache)

* Bien, porque no genera latencia de red; la lectura en memoria dentro del mismo proceso Node.js es instantánea (<1 ms).
* Malo, porque al escalar horizontalmente Cloud Run a múltiples contenedores independientes, cada contenedor tendría una copia local desincronizada, generando discrepancias de horarios entre usuarios.
* Malo, porque aumenta el consumo de memoria heap del contenedor Node.js, elevando el riesgo de cierres por Out-Of-Memory (OOM).

### Lectura Directa en CockroachDB (Follower Reads)

* Bien, porque elimina la necesidad de gestionar un motor de caché externo y garantiza la verdad absoluta desde la base de datos relacional.
* Malo, porque somete a CockroachDB a miles de consultas de lectura en picos de publicación, consumiendo unidades de petición costosas y aumentando la latencia promedio a más de 50-150 ms por consulta.
* Malo, porque no provee la velocidad de acceso en memoria necesaria para que el algoritmo de programación automática resuelva matrices complejas en <3s (Escenario 6.7).

### Base de Datos Documental Auxiliar (MongoDB / DynamoDB)

* Bien, porque maneja documentos JSON desnormalizados con alta velocidad de lectura.
* Malo, porque añade un segundo motor de base de datos completo con lenguaje de consulta, drivers, migraciones y costos de infraestructura desproporcionados para un simple acelerador de lectura.
