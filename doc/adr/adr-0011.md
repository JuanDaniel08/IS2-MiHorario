# Gestión Centralizada de Secretos y Llaves Criptográficas mediante Baúl de Secretos (Secret Manager)

* Estado: Propuesto
* Decidentes: Angie - Daniel
* Fecha: 2026-09-16
* Historia técnica: Escenario 6.8 (Cifrado y Habeas Data) / ESC-TRA-0001 (Auditoría Inmutable) / ESC-INT-0001 (Integración con Microsoft Teams) / ADR-0001 / ADR-0005 / ADR-0006

## Contexto y planteamiento del problema

La plataforma MiHorario interactúa con múltiples componentes de infraestructura y servicios externos que exigen el uso de credenciales de alto privilegio:
1. **Cadena de conexión y certificados TLS de CockroachDB:** Credenciales maestras para acceder a los datos relacionales de empleados y turnos ([ADR-0001](adr-0001.md)).
2. **Llaves criptográficas de firma de Tokens JWT:** Claves privadas (RSA/ECDSA o secretos HMAC) utilizadas por el Proveedor de Identidad ([ADR-0005](adr-0005.md)) para emitir tokens no falsificables.
3. **Credenciales de Redis:** Clave de acceso a la instancia en memoria para colas y caché ([ADR-0004](adr-0004.md) y [ADR-0008](adr-0008.md)).
4. **Tokens de integración externa:** Webhooks y claves de aplicación para Microsoft Teams (**ESC-INT-0001**) y credenciales de servicio JSON para Firebase Cloud Messaging (**Escenario 6.6** y [ADR-0013](adr-0013.md)).

El diagrama de arquitectura define formalmente el componente **Baúl de secretos [Software System]**: *"Almacenamiento y gestión de claves seguras, certificados, tokens de API, llaves y cadenas de conexión de la aplicación"*.

Si estos secretos se almacenan en archivos `.env` planos, se queman en imágenes de Docker o se suben por error a repositorios de código fuente en Git, se generaría un riesgo crítico de filtración que comprometería la información privada de los empleados de Comfama, violando directamente el marco legal de Protección de Datos Personales (Ley 1581 de 2012 - Habeas Data, **Escenario 6.8**) y el principio de inmutabilidad y no repudio de **ESC-TRA-0001**. Asimismo, la falta de un baúl centralizado dificulta la rotación periódica de credenciales ante incidentes de seguridad sin requerir la reconstrucción y re-despliegue de los contenedores.

¿Qué mecanismo centralizado y seguro debe adoptarse para almacenar, rotar, auditar e inyectar de forma controlada las credenciales, llaves criptográficas y secretos de la aplicación?

## Impulsores de decisión

* **Escenario de calidad (Seguridad y Privacidad - Escenario 6.8):** Cifrar todos los secretos en reposo (AES-256) y en tránsito (TLS 1.3), garantizando que nadie sin autorización explícita pueda visualizar las llaves criptográficas o cadenas de conexión.
* **Escenario de calidad (Trazabilidad y Auditoría - ESC-TRA-0001):** Registrar de forma inmutable quién, cuándo y desde qué proceso de cómputo se solicitó el acceso a un secreto específico (registro de auditoría de accesos).
* **Escenario de calidad (Disponibilidad y Operación 24/7 - ESC-DIS-0001 y Escenario 6.5):** Permitir la rotación de credenciales y tokens de API sin interrupción de servicio ni caídas de la aplicación (*Zero-Downtime*).
* **Principio de Menor Privilegio (Least Privilege):** Solo la identidad de servicio (*Service Account*) del contenedor backend en Cloud Run ([ADR-0006](adr-0006.md)) debe tener permisos estrictos de lectura sobre sus secretos específicos.
* **Restricción técnica (Mantenibilidad y Simplicidad de Operación):** Evitar la complejidad y costo de mantener clústeres de almacenamiento de secretos autogestionados que requieran un mantenimiento operativo desproporcionado.

## Opciones consideradas

* Opción 1: Servicio Gestionado de Baúl de Secretos en la Nube con Google Secret Manager integrado con Cloud Run IAM
* Opción 2: Servidor Dedicado de Almacenamiento de Secretos con HashiCorp Vault autohospedado en clúster
* Opción 3: Plataforma SaaS Externa de Gestión de Entornos y Secretos (Doppler / Infisical)
* Opción 4: Variables de Entorno Convencionales inyectadas mediante el Pipeline de CI/CD (GitHub Secrets a variables planas de contenedor)

## Resultado de la decisión

Opción elegida: "Servicio Gestionado de Baúl de Secretos en la Nube con Google Secret Manager integrado con Cloud Run IAM", porque proporciona una solución nativa en la nube, totalmente gestionada, cifrada por hardware (FIPS 140-2 Level 3 con Google Cloud KMS) y sin servidores que administrar, implementando las siguientes capacidades técnicas clave:

1. **Inyección Segura y Enmascarada en Cloud Run:** En lugar de mantener secretos como variables de entorno de texto plano en la configuración del servicio, Cloud Run ([ADR-0006](adr-0006.md)) monta las versiones de los secretos directamente desde Google Secret Manager al arrancar el contenedor:
   - Ya sea como variables de entorno seguras mapeadas dinámicamente (`SECRET_ENV_VAR = secret-manager://projects/.../secrets/db-url/versions/latest`).
   - O como archivos virtuales en memoria montados en disco efímero (`/secrets/firebase-credentials.json`).
2. **Control de Acceso Basado en Identidad (Cloud IAM Least Privilege):** El acceso al baúl de secretos se restringe estrictamente a la cuenta de servicio de backend (`backend-service-account@mihorario.iam.gserviceaccount.com`) mediante el rol `Secret Manager Secret Accessor`. Ningún desarrollador ni cliente externo tiene acceso directo en producción a las llaves de base de datos o JWT.
3. **Versionado de Secretos y Rotación Continua:** Cada secreto admite múltiples versiones simultáneas (`v1`, `v2`). Cuando se actualiza la clave privada de firma JWT o la contraseña de CockroachDB, se publica una nueva versión sin sobreescribir la anterior, permitiendo transiciones suaves de rotación de credenciales sin tiempo de inactividad (*Zero-Downtime*).
4. **Trazabilidad Inmutable en Cloud Audit Logs (ESC-TRA-0001):** Cada lectura, modificación o acceso a un secreto queda registrado de forma indeleble en los registros de auditoría de Google Cloud, capturando la marca de tiempo exacta, la identidad solicitante y el resultado de la operación, cumpliendo a cabalidad con el marco de Habeas Data (Escenario 6.8).
5. **Cero Mantenimiento Operativo y Alta Disponibilidad:** Google garantiza una disponibilidad del 99.95% para Secret Manager con replicación automática multirregional, asegurando que ante cualquier reinicio o auto-escalado de contenedores, las credenciales estén siempre disponibles.

### Consecuencias positivas

* **Eliminación total de secretos en el código fuente:** Se erradica por diseño el riesgo de que tokens de Teams, credenciales de Firebase o contraseñas de CockroachDB se filtren en Git o en el historial de compilación de Docker.
* **Cumplimiento legal estricto de Habeas Data (Escenario 6.8):** Las llaves criptográficas que protegen la información sensible de los colaboradores están custodiadas bajo cifrado de grado militar con claves administradas centralmente.
* **Auditoría completa de accesos (ESC-TRA-0001):** Cualquier intento de acceso no autorizado a los secretos genera alertas inmediatas y registros forenses inmutables.
* **Desacople entre configuración y despliegue:** Cambiar una credencial no exige reconstruir la imagen Docker ni re-compilar el código de NestJS; solo se actualiza la versión en el baúl.

### Consecuencias negativas

* **Acoplamiento con la plataforma Google Cloud:** El uso nativo de Secret Manager afianza la solución con el ecosistema de GCP, aunque la abstracción en el código NestJS mediante una interfaz de repositorio de configuración (*ConfigPort*) permite reemplazar el proveedor por Vault o AWS Secrets Manager si fuera necesario en el futuro.
* **Tiempo de resolución en arranque en frío (*Cold Start*):** En el momento en que un nuevo contenedor de Cloud Run se inicia, la descarga e inyección de los secretos añade una pequeña latencia (alrededor de 50 a 100 milisegundos), la cual queda completamente mitigada gracias a la política de `min-instances = 1` definida en el [ADR-0006](adr-0006.md).

## Pros y contras de las opciones

### Google Secret Manager + Cloud IAM

* Bien, porque cifra los secretos en reposo y en tránsito de forma transparente con HSMs y Cloud KMS (Escenario 6.8).
* Bien, porque se integra de forma directa y nativa con Cloud Run sin necesidad de librerías complejas ni llamadas HTTP manuales en el arranque (ADR-0006).
* Bien, porque ofrece versionado automático de llaves y auditoría inmutable de accesos en Cloud Audit Logs (ESC-TRA-0001).
* Bien, porque es completamente serverless y no genera sobrecarga de administración de servidores.
* Malo, porque genera dependencia del ecosistema de seguridad de Google Cloud Platform.

### HashiCorp Vault Autogestionado

* Bien, porque es el estándar de la industria para entornos multi-nube con generación dinámica de secretos efímeros.
* Malo, porque requiere aprovisionar, monitorear, respaldar y mantener un clúster de alta disponibilidad de Vault (Consul/Raft backend), requiriendo personal de DevOps especializado.
* Malo, porque los costos fijos de cómputo y la complejidad del proceso de "desellado" (*unsealing*) son excesivos para la escala del proyecto MiHorario.

### Plataforma SaaS Externa (Doppler / Infisical)

* Bien, porque provee interfaces web intuitivas para desarrolladores y sincronización fluida entre entornos.
* Malo, porque introduce un tercero adicional fuera del perímetro de red de la nube donde reside el backend, añadiendo costos recurrentes de suscripción mensual por usuario desarrollador.

### Variables de Entorno Planas en CI/CD

* Bien, porque es el método más simple y no requiere servicios adicionales.
* Malo, porque los secretos quedan almacenados en texto plano en la configuración del contenedor, visibles para cualquier persona con acceso a la consola de despliegue.
* Malo, porque no ofrece versionado ni rotación dinámica; cualquier cambio de clave obliga a re-desplegar la aplicación.
