# Usar CockroachDB para la base de datos

* Estado: Propuesto
* Decidentes: Angie - Daniel
* Fecha: 2026-09-09
* Historia técnica: ESC-DIS-0001 / ESC-REN-0007 / Escenario 6.1 (Validación de Duplicaciones y Choques)

## Contexto y planteamiento del problema

Al organizar los turnos del personal en la plataforma MiHorario, un empleado no puede cumplir con dos jornadas laborales a la misma hora. Actualmente, existe el riesgo de que dos administradores o procesos concurrentes asignen y publiquen turnos que se solapen en el tiempo para un mismo trabajador, generando inconsistencias en la nómina, problemas de cobertura y reclamos laborales.

El sistema requiere garantizar consistencia transaccional estricta (aislamiento serializable para evitar cruces de horarios en concurrencia) y alta disponibilidad continua (>99.9%), pero al mismo tiempo el equipo necesita minimizar los costos fijos de infraestructura en fases iniciales, evitar el bloqueo de proveedor (*vendor lock-in*) y facilitar el desarrollo local y las pruebas con herramientas estándar de la industria.

¿Qué motor de base de datos deberíamos utilizar para garantizar consistencia transaccional distribuida estricta (evitando cruces de horarios), alta disponibilidad y excelente experiencia de desarrollo con costos optimizados?

## Impulsores de decisión

* **Escenario de calidad (Confiabilidad y Consistencia - Escenario 6.1):** El sistema debe garantizar aislamiento transaccional estricto (serializabilidad ACID) y soporte para validación en base de datos ("Doble Candado"), evitando al 100% solapamientos o duplicaciones de turnos incluso ante solicitudes simultáneas de publicación.
* **Escenario de calidad (Disponibilidad - ESC-DIS-0001):** La plataforma requiere una disponibilidad mínima del 99.9% mensual sin interrupciones por mantenimientos no programados o fallas de zona.
* **Escenario de calidad (Rendimiento y Concurrencia - ESC-REN-0007):** El sistema debe responder en menos de 2 segundos manteniendo consistencia operativa bajo una carga simultánea de al menos 100 usuarios activos consultando y publicando la agenda.
* **Restricción técnica (Compatibilidad y Ecosistema de Desarrollo):** Debe ofrecer soporte fluido para herramientas y ORMs estándar del ecosistema Node.js/TypeScript (Prisma, TypeORM) mediante compatibilidad con el protocolo de PostgreSQL (`pgwire`), permitiendo entornos locales con Docker sin emuladores complejos.
* **Restricción de negocio (Presupuesto y Vendor Lock-in):** Minimizar el costo base mensual de operación mediante esquemas *Serverless* o de bajo costo en fases tempranas, preservando la portabilidad multi-nube sin atarse de forma exclusiva a la infraestructura de un solo proveedor.

## Opciones consideradas

* Opción 1: CockroachDB (CockroachDB Serverless / Cloud)
* Opción 2: Google Cloud Spanner
* Opción 3: PostgreSQL gestionado (Cloud SQL / AWS RDS para PostgreSQL)
* Opción 4: MongoDB Atlas

## Resultado de la decisión

Opción elegida: "CockroachDB", porque es una base de datos relacional distribuida (NewSQL) nativa en la nube, con compatibilidad completa con el protocolo y dialecto de PostgreSQL (pgwire), y soporte para transacciones ACID estrictas con aislamiento *Serializable* distribuido basado en el algoritmo de consenso Raft y Relojes Lógicos Híbridos (HLC). 

Esto elimina de raíz las condiciones de carrera y la doble asignación de horarios concurrentes mediante la técnica de "Doble Candado" (Escenario 6.1), al tiempo que ofrece una disponibilidad superior al 99.99% con replicación automática entre zonas sin intervención manual (ESC-DIS-0001). A diferencia de Google Cloud Spanner, CockroachDB ofrece una modalidad *Serverless* con capa gratuita generosa que reduce a cero el costo base de entrada, no genera bloqueo con ningún proveedor cloud y se integra de forma transparente con NestJS y Prisma ORM.

### Consecuencias positivas

* **Consistencia serializable estricta:** Garantiza que dos transacciones simultáneas de asignación de turnos sobre un mismo empleado se aíslen formalmente, impidiendo el solapamiento de horarios (Escenario 6.1).
* **Alta disponibilidad nativa y tolerancia a fallos:** El consenso Raft replica los datos en múltiples nodos y zonas geográficas. La pérdida de un nodo no genera indisponibilidad ni pérdida de transacciones confirmadas, superando el 99.9% de SLA (ESC-DIS-0001).
* **Compatibilidad con PostgreSQL (pgwire):** Permite utilizar librerías estándar como Prisma ORM o TypeORM en el backend NestJS ([ADR-0002](adr-0002.md)), simplificando migraciones, consultas tipadas y modelos relacionales.
* **Excelente experiencia de desarrollo local:** Los desarrolladores pueden levantar una instancia de CockroachDB idéntica a producción en sus máquinas locales con un comando simple de Docker Compose (`cockroach start-single-node --insecure`).
* **Optimización drástica de costos (Serverless):** CockroachDB Serverless escala a cero y factura únicamente por las unidades de petición (Request Units) y almacenamiento consumidos, con un nivel gratuito mensual que cubre ampliamente el desarrollo, pruebas y despliegue inicial.
* **Portabilidad y cero Vendor Lock-in:** La base de datos puede ejecutarse en CockroachDB Cloud (en regiones de GCP, AWS o Azure), autohospedarse en Kubernetes o migrarse a PostgreSQL estándar si las necesidades futuras cambiaran.

### Consecuencias negativas

* **Reintentos de transacción por contención:** Debido a que CockroachDB fuerza serializabilidad estricta por defecto, cuando dos administradores intentan modificar la agenda del mismo empleado en el mismo milisegundo, la base de datos aborta una de las transacciones con un error de reintento (`40001 - serialization_failure`), lo cual exige configurar lógica de reintento automático (*retry loop*) en el repositorio de NestJS.
* **Latencia de consenso en escrituras distribuidas:** Cada escritura requiere quórum de nodos vía Raft, lo que añade una pequeña sobrecarga de latencia de red en escrituras frente a un PostgreSQL mono-nodo tradicional (aunque permanece ampliamente por debajo del límite de 2 segundos de ESC-REN-0007).
* **Licenciamiento Business Source License (BSL):** Para implementaciones autogestionadas a gran escala comercial, el código fuente se rige bajo licencia BSL, aunque su uso en CockroachDB Cloud y clústeres comunitarios estándar es completamente libre.

## Pros y contras de las opciones

### CockroachDB

Base de datos NewSQL distribuida, compatible con el protocolo PostgreSQL y orientada a resiliencia global.

* Bien, porque garantiza aislamiento serializable estricto y atomicidad ACID distribuida, impidiendo cruces de turnos concurrentes (Confiabilidad y Consistencia).
* Bien, porque es compatible con PostgreSQL, permitiendo utilizar Prisma ORM de forma nativa en NestJS.
* Bien, porque ofrece disponibilidad del 99.99% con conmutación por error automática sin caída de servicio (Disponibilidad ESC-DIS-0001).
* Bien, porque su modalidad Serverless permite comenzar a costo cero con facturación elástica por uso real.
* Bien, porque no genera atadura a un único proveedor de nube (Portabilidad Multi-cloud).
* Malo, porque requiere manejar reintentos automáticos en el backend ante errores de serialización concurrentes.

### Google Cloud Spanner

Base de datos NewSQL distribuida propietaria de Google Cloud Platform basada en tecnología TrueTime.

* Bien, porque ofrece la mayor consistencia externa del mercado mediante sincronización de relojes atómicos por hardware.
* Bien, porque escala de forma elástica y transparente a volúmenes masivos de datos globales.
* Malo, porque su costo operativo base es muy alto (mínimo >$60–$200 USD/mes), resultando ineficiente para el presupuesto de un proyecto en fase inicial o media.
* Malo, porque genera dependencia tecnológica y comercial exclusiva con Google Cloud Platform (Vendor Lock-in total).
* Malo, porque su ecosistema de ORMs en Node.js es más limitado y complejo que el estándar de PostgreSQL.

### PostgreSQL gestionado (Cloud SQL / RDS)

Base de datos relacional open-source clásica ejecutada como servicio administrado en una sola instancia con réplicas de lectura.

* Bien, porque es el estándar universal de la industria con máxima madurez y compatibilidad total de herramientas.
* Bien, porque tiene un costo moderado y predecible en instancias pequeñas.
* Malo, porque la escalabilidad horizontal de operaciones de escritura no es nativa y requiere sharding manual complejo.
* Malo, porque la conmutación por error (*failover*) de alta disponibilidad en bases de datos activo-pasivo tradicionales introduce ventanas transitorias de indisponibilidad (de 30 a 120 segundos) durante caídas de zona.

### MongoDB Atlas

Base de datos NoSQL orientada a documentos distribuida y gestionada en la nube.

* Bien, porque su esquema flexible permite adaptar con rapidez estructuras dinámicas de jornadas laborales.
* Bien, porque escala horizontalmente de forma nativa mediante particionamiento de colecciones.
* Malo, porque su modelo de consistencia y sobrecarga en transacciones multi-documento eleva el riesgo de condiciones de carrera durante la asignación simultánea de turnos.
* Malo, porque carece de restricciones relacionales de unicidad temporal compuesta a nivel de motor para garantizar el "Doble Candado".
