# Implementación de API Gateway y Enrutamiento con Service Discovery para la Gestión Unificada de Tráfico

* Estado: Propuesto
* Decidentes: Angie - Daniel
* Fecha: 2026-09-16
* Historia técnica: Restricción Técnica Sección 3 (Prácticas de Diseño: Arquitectura Modular/Microservicios) / ESC-REN-0007 (Concurrencia de 100 Usuarios) / ESC-DIS-0001 (Disponibilidad 99.9%) / ADR-0003 / ADR-0005 / ADR-0006

## Contexto y planteamiento del problema

En la arquitectura de MiHorario, diversos clientes (la aplicación web SPA en React.js, navegadores móviles de operarios en campo y potenciales webhooks institucionales de Comfama) requieren comunicarse con las APIs del backend para consultar agendas, autenticarse, aprobar cambios de turno y despachar notificaciones.

Si los clientes web y móviles se conectan directamente a las URLs o direcciones de red internas de los servicios de backend:
1. Se expone la topología interna del sistema, incrementando la superficie de ataque.
2. Cada servicio o módulo tendría que implementar de forma duplicada e independiente políticas transversales de seguridad: terminación TLS/SSL, cabeceras CORS, validación previa de tokens JWT, limitación de tasa (*Rate Limiting*) y recolección de métricas de acceso.
3. Se restringe la evolución arquitectónica: la **Restricción Técnica de la Sección 3** exige *"Propender por el uso de arquitectura basada en microservicios o modular"*. Si en el futuro un módulo como `Notifications` o `AutomaticScheduling` se extrae a un servicio independiente fuera del monolito modular ([ADR-0003](adr-0003.md)), los clientes tendrían que cambiar sus URLs de destino, rompiendo los contratos de integración.
4. Se requiere un mecanismo de **Service Discovery** que permita resolver dinámicamente las instancias saludables de los servicios sin depender de direcciones IP estáticas frágiles.

¿Qué patrón y tecnología de punto de entrada debe adoptarse para centralizar el enrutamiento de tráfico, enmascarar la infraestructura interna, proveer descubrimiento dinámico de servicios y aplicar políticas transversales de tráfico?

## Impulsores de decisión

* **Restricción técnica (Prácticas de Diseño - Sección 3):** Propender por el uso de arquitectura basada en microservicios o modular, permitiendo desacoplar el enrutamiento del cliente de la ubicación física de los servicios.
* **Escenario de calidad (Seguridad y Control Perimetral - ESC-ADM-0002 y Escenario 6.8):** Proveer un punto único de entrada seguro donde se aplique terminación SSL, validación previa de tokens de autenticación y aislamiento de la red privada de backend.
* **Escenario de calidad (Rendimiento y Disponibilidad - ESC-REN-0007 y ESC-DIS-0001):** Gestionar el balanceo de carga, la reconexión automática y el enrutamiento de tráfico con baja latencia adicional (<5 ms) manteniendo SLA del 99.9%.
* **Restricción técnica (Mantenibilidad y Simplicidad de Operación):** Evitar la administración manual de clústeres complejos de balanceadores que añadan sobrecarga de DevOps desmedida al equipo de desarrollo.
* **Trazabilidad y Observabilidad:** Centralizar los logs de acceso HTTP, códigos de estado, latencias de petición y correlación de solicitudes (*Correlation IDs*) antes de ingresar a los contenedores.

## Opciones consideradas

* Opción 1: API Gateway Gestionado en la Nube (Google Cloud API Gateway / Envoy Proxy gestionado) con Service Discovery integrado en Cloud Run
* Opción 2: Pasarela de API Dedicada de Código Abierto (Kong Gateway / Apache APISIX) desplegada en contenedores
* Opción 3: Servidor Proxy Inverso Autogestionado con Nginx tradicional
* Opción 4: Conexión Directa Cliente-Servicio sin API Gateway (Exposición directa del contenedor de NestJS)

## Resultado de la decisión

Opción elegida: "API Gateway Gestionado en la Nube (Google Cloud API Gateway / Envoy Proxy gestionado) con Service Discovery integrado en Cloud Run", porque provee una puerta de enlace serverless, altamente disponible y sin mantenimiento de infraestructura que se integra de manera nativa con el modelo de contenedores gestionados ([ADR-0006](adr-0006.md)):

1. **Punto Único de Entrada y Enmascaramiento:** Todos los clientes externos apuntan a un dominio unificado (`https://api.mihorario.comfama.com`). El API Gateway intercepta todo el tráfico entrante, valida las cabeceras CORS de forma centralizada y enruta las peticiones basándose en especificaciones estándar de OpenAPI (Swagger):
   - `/v1/auth/*` -> Enrutado hacia el módulo de autenticación / IAM.
   - `/v1/schedules/*` -> Enrutado hacia el módulo de turnos y agendas.
   - `/v1/notifications/*` -> Enrutado hacia el servicio de despacho de eventos.
2. **Service Discovery Dinámico Nativo:** Al integrarse con la infraestructura de Cloud Run ([ADR-0006](adr-0006.md)), el descubrimiento de servicios se gestiona automáticamente mediante DNS interno y el registro de revisiones de Google Cloud Service Directory. Cuando un servicio escala de 1 a N instancias o se despliega una nueva revisión (*Zero-Downtime*), el Gateway descubre dinámicamente los contenedores saludables sin requerir un clúster de Consul o Eureka autogestionado.
3. **Validación Previa de Autenticación y Rate Limiting:** El API Gateway valida la firma criptográfica de los tokens JWT emitidos por el Proveedor de Identidad ([ADR-0005](adr-0005.md)) antes de reenviar la petición al backend. Si el token es inválido o está expirado, el Gateway rechaza la petición con código 401 en el borde, impidiendo que peticiones no autorizadas consuman CPU del backend NestJS.
4. **Camino Evolutivo Hacia Microservicios (Restricción Sección 3):** Si en fases futuras un módulo del monolito modular ([ADR-0003](adr-0003.md)) requiere ser extraído a un microservicio independiente con escalado propio (ej. el cálculo de asignación automática de turnos), basta con actualizar la regla de reescritura de ruta en el API Gateway; los clientes web y móviles continúan consumiendo la misma URL pública sin enterarse del cambio de infraestructura interna.

### Consecuencias positivas

* **Aislamiento perimetral:** El contenedor de backend de NestJS puede configurarse con acceso restringido (*Private Ingress*), permitiendo únicamente tráfico proveniente del API Gateway y blindando los servicios de accesos no autorizados directos por internet.
* **Cero sobrecarga de administración:** Cloud API Gateway es 100% serverless, escala elásticamente de forma automática y factura por volumen de peticiones, garantizando un SLA del 99.95% sin necesidad de parchar sistemas operativos ni configurar balanceadores a mano.
* **Descubrimiento y conmutación por error transparente:** Si una instancia de contenedor falla, el Service Discovery interno redirige el tráfico inmediatamente a instancias sanas en menos de 100 milisegundos.
* **Centralización de CORS, SSL y Políticas de Entrada:** Elimina la duplicación de código de configuración de certificados y dominios en cada servicio de backend.

### Consecuencias negativas

* **Salto de red adicional (Hop):** Añade una pequeña latencia de intermediación (habitualmente entre 2 y 5 milisegundos), la cual es perfectamente despreciable frente al límite holgado de 2 segundos exigido por ESC-REN-0007.
* **Dependencia de la especificación OpenAPI:** Toda modificación o incorporación de nuevas rutas públicas de API debe mantenerse reflejada en el archivo de especificación de OpenAPI del Gateway para que el enrutador conozca el mapeo hacia los servicios de destino.

## Pros y contras de las opciones

### Cloud API Gateway + Service Discovery Nativo

* Bien, porque es 100% gestionado y serverless, reduciendo a cero el costo de mantenimiento operacional de DevOps.
* Bien, porque realiza validación de tokens JWT en el perímetro, protegiendo al backend de solicitudes inválidas.
* Bien, porque resuelve el Service Discovery dinámico de revisiones de Cloud Run de manera nativa (ADR-0006).
* Bien, porque habilita el desacoplamiento necesario para transicionar de monolito modular a microservicios según la Restricción Sección 3.
* Malo, porque requiere sincronizar los cambios de endpoints mediante definiciones OpenAPI.

### Kong Gateway Autogestionado en Contenedor

* Bien, porque es extremadamente potente y extensible mediante plugins de Lua para políticas avanzadas de tráfico.
* Malo, porque requiere desplegar, mantener y pagar una instancia de base de datos dedicada (PostgreSQL) para guardar su configuración y estado, o gestionarlo en modo *DB-less* complejo.
* Malo, porque añade sobrecarga de parches, monitoreo y dimensionamiento de nodos para un equipo de ingeniería ágil.

### Proxy Inverso con Nginx Tradicional

* Bien, porque es una tecnología probada, ligera y de alto rendimiento para balanceo y reescritura de URLs.
* Malo, porque no cuenta con Service Discovery dinámico nativo para contenedores serverless efímeros sin scripts adicionales de recarga de configuración.
* Malo, porque no realiza validación nativa de tokens JWT sin compilar módulos comerciales (Nginx Plus).

### Conexión Directa Cliente-Servicio (Sin Gateway)

* Bien, porque elimina cualquier salto de red intermedio y simplifica la topología inicial.
* Malo, porque acopla fuertemente el frontend a la URL de un solo backend monolítico, violando la directriz de evolución hacia microservicios de la Restricción Sección 3.
* Malo, porque obliga a exponer el backend a internet público y procesar SSL, CORS y peticiones inválidas directamente en el hilo de ejecución de NestJS.
