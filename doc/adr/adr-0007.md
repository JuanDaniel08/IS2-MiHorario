# Adopción de React.js (SPA con Vite) y Distribución de Contenido Estático mediante Red de Distribución de Contenidos (CDN)

* Estado: Propuesto
* Decidentes: Angie - Daniel
* Fecha: 2026-09-16
* Historia técnica: ESC-REN-0001 (Carga Inicial y Renderizado en Redes Móviles) / ESC-ACC-0002 (Accesibilidad Visual y Codificación Cromática) / ESC-DIS-0001 (Disponibilidad 99.9%) / ADR-0002 / ADR-0006

## Contexto y planteamiento del problema

La plataforma MiHorario cuenta con dos perfiles de usuario que interactúan intensamente con interfaces complejas de calendario: los administradores que orquestan, arrastran y editan mallas horarias para más de 50 colaboradores simultáneos, y los empleados u operarios que consultan sus turnos asignados desde teléfonos móviles en campo bajo redes celulares (4G estándar o redes con ancho de banda variable en las instalaciones del parque Comfama).

Conforme al requerimiento **ESC-REN-0001**, el tiempo de carga inicial y renderizado del calendario visual no debe superar los 2 segundos en redes móviles. Al mismo tiempo, la visualización de la malla exige reactividad fluida en el navegador, renderizado condicional con codificación cromática para distinguir horas ordinarias, recargos nocturnos, dominicales y descansos (**ESC-ACC-0002**), así como capacidades de actualización dinámica sin recargas completas de página que degraden la experiencia del usuario.

Por otra parte, servir los archivos estáticos (HTML, CSS empaquetado, scripts JavaScript, iconos y fuentes tipográficas) directamente desde el contenedor del backend en NestJS saturaría los recursos de cómputo del servidor con peticiones de I/O triviales, aumentando innecesariamente el costo de Cloud Run y poniendo en riesgo el SLA de disponibilidad del 99.9% (**ESC-DIS-0001**).

¿Qué tecnología de frontend y estrategia de entrega de contenido estático debe seleccionarse para garantizar renderizado interactivo ultrarrápido (<2s en redes móviles), tipado unificado con el backend y óptima distribución global desacoplada de la capa de cómputo?

## Impulsores de decisión

* **Escenario de calidad (Rendimiento en Redes Móviles - ESC-REN-0001):** El tiempo de renderizado y carga inicial del calendario visual no debe superar los 2 segundos operando sobre redes 4G estándar.
* **Escenario de calidad (Usabilidad y Accesibilidad - ESC-ACC-0002):** La interfaz debe soportar renderizado interactivo en tiempo real con codificación cromática (verde para ordinarias, azul para recargos, rojo para excesos) y componentes accesibles que no congelen el navegador.
* **Escenario de calidad (Disponibilidad y Rendimiento - ESC-DIS-0001):** Descargar la entrega de archivos estáticos del servidor de aplicaciones para evitar cuellos de botella de ancho de banda y garantizar distribución de alta disponibilidad con tolerancia a fallos.
* **Restricción técnica (Mantenibilidad y Ecosistema TypeScript):** Aprovechar la unificación tecnológica con el backend NestJS ([ADR-0002](adr-0002.md)) compartiendo interfaces de TypeScript, modelos DTO y validaciones comunes.
* **Restricción de negocio (Time-to-Market y Costo):** Maximizar la productividad del equipo con herramientas de construcción rápidas y despliegue de bajo costo en infraestructura serverless o almacenamiento de borde (*Edge Storage*).

## Opciones consideradas

* Opción 1: Single Page Application (SPA) con React.js + Vite, distribuida globalmente a través de Content Delivery Network (CDN) y almacenamiento de objetos
* Opción 2: Framework Fullstack con Server-Side Rendering (SSR) mediante Next.js
* Opción 3: Renderizado Tradicional del lado del Servidor (SSR) con NestJS y motores de plantillas (Handlebars / EJS)
* Opción 4: Single Page Application con Angular Framework distribuido en Nginx tradicional

## Resultado de la decisión

Opción elegida: "Single Page Application (SPA) con React.js + Vite, distribuida globalmente a través de Content Delivery Network (CDN) y almacenamiento de objetos", porque desacopla tajantemente la entrega de los artefactos visuales de la ejecución de lógica de negocio, optimizando el rendimiento y la disponibilidad bajo las siguientes consideraciones técnicas:

1. **Ecosistema React y Reactividad en Componentes Complejos:** React cuenta con el ecosistema de componentes de calendario y manipulación de mallas más maduro de la industria (FullCalendar, TanStack Table/Virtual, Radix UI). Su modelo de Virtual DOM y hooks reactivos permite actualizar únicamente las celdas de turnos modificadas sin re-renderizar la tabla completa, cumpliendo con la codificación cromática y accesibilidad visual de ESC-ACC-0002.
2. **Empaquetado y Optimización con Vite:** Vite utiliza Rollup con *tree-shaking* agresivo, compresión Brotli/Gzip, división de código por rutas (*code-splitting*) y pre-empaquetado con esbuild. Esto produce *bundles* de JavaScript ultraligeros (<150 KB en la carga inicial), garantizando que en dispositivos móviles 4G el First Contentful Paint (FCP) y el Time to Interactive (TTI) se ubiquen holgadamente por debajo de los 2 segundos de ESC-REN-0001.
3. **Distribución en el Borde mediante Content Delivery Network (CDN):** Los archivos estáticos compilados (`index.html`, `bundle.js`, `style.css`) se almacenan en un bucket de almacenamiento de objetos (Google Cloud Storage / AWS S3) conectado a una red CDN global (Cloudflare / Google Cloud CDN). La CDN cachea los activos en cientos de puntos de presencia (*Points of Presence - PoPs*) geográficamente cercanos al usuario (incluyendo nodos en Bogotá/Medellín para Comfama), entregando el contenido con latencias inferiores a 50 ms y con disponibilidad >99.99%, sin tocar el contenedor de backend.
4. **Unificación con TypeScript:** Al compartir TypeScript con el backend NestJS ([ADR-0002](adr-0002.md)), los contratos de DTOs, tipos de turnos y estados de solicitud se sincronizan de forma directa, eliminando errores de discrepancia entre cliente y servidor.

### Consecuencias positivas

* **Cumplimiento estricto de ESC-REN-0001:** La entrega de activos estáticos desde la caché del PoP de la CDN sumada a la ligereza del bundle de Vite permite cargar el shell de la aplicación en menos de 1 segundo en redes 4G.
* **Cero sobrecarga en el Backend NestJS:** El contenedor de Cloud Run ([ADR-0006](adr-0006.md)) se dedica exclusivamente a resolver peticiones de API JSON y lógica de negocio, reduciendo el consumo de memoria RAM y CPU del backend.
* **Escalabilidad infinita de la capa visual:** La CDN absorbe millones de peticiones concurrentes de archivos CSS/JS/HTML sin riesgo de degradación ni costos elevados de cómputo.
* **Actualizaciones inmediatas con invalidación de caché:** Los archivos estáticos empaquetados incluyen hash de contenido en su nombre (`app.[hash].js`), permitiendo caché inmutable a largo plazo (*cache-control: immutable*) para activos versionados y un archivo `index.html` ligero que se actualiza instantáneamente tras cada despliegue.

### Consecuencias negativas

* **Carga diferida de datos vía API:** Al ser una SPA, el navegador debe descargar primero el paquete JS y luego realizar peticiones asíncronas vía API Gateway ([ADR-0009](adr-0009.md)) para obtener los turnos de la base de datos, lo que requiere manejar estados de carga visual (*skeletons/spinners*) para evitar parpadeos visuales.
* **Configuración de enrutamiento SPA en la CDN:** El servidor de la CDN o bucket de almacenamiento debe configurarse para redirigir todas las rutas desconocidas a `index.html` (Fallback routing / rewrite rule) para permitir que el enrutador del cliente (`react-router-dom`) maneje las URLs limpias.

## Pros y contras de las opciones

### React.js + Vite con CDN

* Bien, porque el empaquetado con Vite genera paquetes ultraligeros con inicio rápido, cumpliendo con el tiempo de carga <2s en 4G (ESC-REN-0001).
* Bien, porque la distribución en CDN entrega archivos estáticos desde puntos de presencia cercanos al usuario con latencias de red mínimas y disponibilidad superior al 99.99%.
* Bien, porque React ofrece componentes maduros para renderizado de calendarios interactivos y accesibilidad cromática (ESC-ACC-0002).
* Bien, porque unifica el lenguaje TypeScript y las definiciones de tipos con el backend NestJS (ADR-0002).
* Malo, porque requiere configurar invalidación de caché y redirecciones a index.html en la CDN para soportar navegación del lado del cliente.

### Next.js (SSR / Hybrid)

* Bien, porque entrega el HTML inicial pre-renderizado desde el servidor, acelerando la visualización del primer contenido.
* Malo, porque requiere mantener instancias de servidor Node.js adicionales o funciones serverless activas para procesar cada petición de renderizado, incrementando significativamente la complejidad operativa y los costos de nube frente a un hosting estático en CDN.
* Malo, porque la ventaja de SEO de SSR no es prioritaria para una aplicación privada de gestión operativa de turnos con acceso restringido tras autenticación (ADR-0005).

### Renderizado Tradicional con NestJS + Plantillas (Handlebars / MVC)

* Bien, porque mantiene todo el código en un único proyecto sin herramientas de construcción independientes para el frontend.
* Malo, porque cualquier interacción dinámica (arrastrar turnos, filtros por área, validación visual en tiempo real) requiere recargas de página o código imperativo con JavaScript plano difícil de mantener.
* Malo, porque recarga el servidor backend con la compilación y entrega de HTML/CSS en cada petición, afectando el tiempo de respuesta bajo alta concurrencia (ESC-REN-0007).

### Angular con Nginx Tradicional

* Bien, porque Angular ofrece una estructura robusta fuertemente tipada con TypeScript y componentes estructurados.
* Malo, porque el peso inicial del *bundle* de Angular es considerablemente más pesado que React con Vite, dificultando alcanzar el límite de 2 segundos en redes móviles 4G (ESC-REN-0001).
* Malo, porque alojarlo en un servidor Nginx en máquina virtual añade costos fijos de mantenimiento, parches del sistema operativo y balanceo manual no alineado con la directriz serverless (ADR-0006).
